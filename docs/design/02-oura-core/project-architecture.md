# Data from Oura 工程方案与开发约束

本文汇总已讨论的分层、目录和实施约束，作为后续开发的设计依据。目录树是目标结构，不表示功能已经实现；按实际开发逐步创建文件，不为未来功能添加空实现。具体数据库字段以 [数据库设计](database-schema.md) 和后续迁移为准。

## 产品范围

应用使用 Oura 开放 API 获取用户授权且平台允许访问的数据，保存到本地独立模型，供脚本、Skill、CLI 和未来 Web 使用。认证信息集中保存在一个认证数据库，每个 Oura 账号使用独立的记录数据库。基础同步指定账号、数据项目和起止时间；全量同步接受起始时间并覆盖可访问的数据项目，以执行时确定的时间为结束边界。

## 目标目录

```text
oura_app/
├── action/
│   ├── operations/          # 应用操作，供各种入口统一调用
│   ├── cli/                 # 命令行协议、交互和呈现
│   └── web/                 # 将来的 Web / HTTP 适配
├── core/
│   ├── account/             # 账号、授权生命周期与认证库业务
│   └── record/              # 健康数据、同步和记录库业务
├── link/
│   └── oura_v2/             # Oura v2 协议与接口封装
├── common/                  # 可复用的通用能力和第三方依赖适配
├── config/                  # 独立的配置加载与校验
└── resource/                # 随应用分发的静态资源和数据库迁移
    └── migrations/
        ├── auth/            # 认证库迁移
        └── record/          # 每账号记录库迁移
```

将 `action/action/` 改名为 **`action/operations/`**：它直接表达目录中是一组供入口调用的基础操作，避免重复名称。保留 `action/` 作为入口层的总目录。

## 层级职责与依赖

```text
CLI / Web / Skill / 脚本
            ↓
    action/operations
            ↓
  core/account + core/record
            ↓
      link/oura_v2 → Oura

common 与 config 为独立的支持模块；resource 提供静态资源。
```

- **入口**：`action/cli/` 和 `action/web/` 只将协议输入转换成操作参数，并将结果或错误转换为相应输出。它们只能调用 `action/operations/` 暴露的应用操作，不直接调用 Core、Link 或数据库。未来 Skill、脚本入口遵守同一规则；程序运行所需的参数解析由各入口负责。
- **操作**：`action/operations/` 是统一的应用调用边界。负责参数和结果契约、必要的轻量编排，调用 Core 方法；不直接调用 Link，不实现具体业务规则，不处理终端或 HTTP 输入输出。初始化、登录、账号状态、范围同步、全量同步及进度查询均应通过这里提供。依赖创建和配置注入集中在操作层的组装入口，供调用者通过操作层获得可用服务。
- **Core**：按业务划分。`account/` 负责账号身份、认证信息、Token 生命周期与认证库；`record/` 负责本地健康数据、数据映射、查询分析和同步状态。Core 定义业务行为与本地数据模型，调用 Link 获取或授权上游数据，使用持久化能力维护本地数据。同步初期归 `record/`；只有规模确实需要时再拆分。
- **Link**：`link/oura_v2/` 负责 Oura OAuth 协议、Token 请求、API 请求、分页及平台错误，不依赖 Core、入口或本地数据库。它返回平台协议数据；Core 中靠近对应业务的映射代码负责转换为本地模型。按平台添加目录，避免在此阶段提前设计复杂插件体系。
- **Common**：提供通用工具或第三方依赖适配，例如通用数据对象基类、加解密、序列化、SQLite 连接、系统密钥库和通用错误基类。数据对象基类只处理通用字段映射和读写；账号、记录等业务对象继承基类并在各自 Core 模块定义。按能力拆分，避免通用 `tools.py` 堆积业务；无跨业务复用价值的规则留在对应模块。Common 不依赖 Action、Core 或 Link；`common/storage.py` 根据运行配置解析数据目录，因此依赖独立 Config。
- **Config**：独立封装环境选择、配置加载、覆盖、校验及配置模型，不归入 Common。负责提供配置值，不包含业务逻辑、API 请求或数据库操作；由组装入口加载并注入各组件，业务模块不自行读取命令行参数。
- **Resource**：存放随应用分发的 SQL 迁移等静态文件，不存放运行时数据库、凭据或日志。源码和打包运行均应能定位资源。

以上约束针对应用内部调用；标准库、通用类型及测试工具可在需要时使用。依赖只沿所示方向流动，不允许下层反向依赖调用入口，也不让 CLI / Web 穿透操作层访问 Core。

## 操作契约与错误处理

操作方法使用明确的输入参数和结构化结果：例如账号标识、同步项目、时间范围及各项目的状态、计数和错误。具体签名与返回类型在实现各功能时确定；同一操作供不同入口复用。交互式登录应将授权地址、回调结果和最终状态以可供入口处理的方式暴露，避免在 Core 或操作方法里直接打印、打开浏览器或读取终端。

Link 将上游协议和 HTTP 失败转为可识别的错误；Core 表达账号、记录和同步业务错误；操作层将其整理为稳定、可识别的调用结果或错误。CLI 和 Web 各自决定显示与状态码。必要时在 `common/` 定义最小错误基类、错误码及安全格式化，具体错误留在所属模块。不得将 Token、客户端密钥、完整回调地址或健康数据写入错误和日志。

## 数据、映射与同步约束

- 本地模型独立设计，映射代码放在 `core/account/` 或 `core/record/` 对应业务附近，明确来源字段、单位、日期与时区语义；上游原始响应不得静默丢弃未知字段。原始记录的保留和删除行为需与隐私政策和实际需求一致。
- 范围同步按数据项目、时间范围处理分页、重复数据和部分失败；个人信息和设备配置等不支持日期过滤的接口应明确采用相应的完整快照语义。全量同步复用范围同步能力，并报告不支持、未授权或失败的项目，不将部分成功报告为完全成功。
- 本地写入应支持重复同步与事务恢复；按上游可靠标识或明确的采样去重策略处理重复数据。不得将未返回的记录直接视为已删除。时间范围、时区边界和同步记录的含义在实现时按各接口明确。
- 认证库与每账号记录库分别维护迁移版本和迁移脚本。开发阶段以简洁实现为先，结构变更可清理测试数据库后重新初始化；正式发布后再按需设计升级迁移。失败不得静默标记成功。认证库和记录库不共享事务，跨库创建、失败清理及恢复策略需单独测试。
- 用户授权、权限不足、Token 过期及刷新、限流和重试必须可辨识；不要在测试或版本库中使用真实凭据、Token 或健康数据。

## 配置约束

`config/` 独立于 `common/`。保留既有环境行为：`OURA_ENV` 可显式选择 local、dev、test、prod；未指定时按 local → dev → test → prod 选择第一个存在的环境文件。对应的私有覆盖文件和进程环境变量按现有规则生效；敏感信息只保存在被忽略的私有配置或安全注入环境中。重构不得改变现有优先级和登录行为，除非另行明确并更新文档。

## 现有代码迁移方案

| 当前能力 | 目标位置 | 迁移要求 |
| --- | --- | --- |
| `action/__main__.py` | `action/cli/` + `action/operations/` + Core | 将交互、应用操作和业务拆开；保留 `python -m oura_app.action` 兼容入口 |
| `action/deadline.py` | 依据使用场景放在登录操作或 `common/` | 保留现有超时与不接受迟到结果的行为；通用化以实际需要为准 |
| `link/oura_v2/api.py`、`core/account/callback.py` | `link/oura_v2/`、`core/account/` | 保留 OAuth、回调和 API 行为，按职责拆分 |
| `core/database.py`、`core/security.py` | `core/account/`、`core/record/` 与 `common/` | 区分业务、存储和密钥库适配；保留现有数据库和加密密钥可读性 |
| `core/auth.sql`、`core/account.sql` | `resource/migrations/auth/`、`resource/migrations/record/` | 开发阶段使用当前初始化结构，不为历史测试数据保留兼容逻辑 |
| `config.py` | 独立 `config/` | 保持项目根目录定位、配置优先级和私有配置保护 |

保留用户已创建的目录和未提交改动；开发测试数据库可按需清理重建，本地应用配置保留。需要更改现有接口时，先确认调用方并提供兼容或说明迁移方式。

## 开发顺序与验收

1. 按目录和依赖约束迁移现有初始化与登录功能；保留原命令和已有数据，更新目录说明与贡献指南。
2. 验证认证库和记录库的新建、重复执行和失败回滚；正式发布前再规划版本升级。
3. 实现指定项目和起止时间的同步能力，包括数据映射、分页、幂等保存及可观察的部分失败。
4. 在基础同步上封装全量同步；随后按需求增加查询、分析、Web 或 Skill 入口。

每阶段运行相关离线测试，使用临时数据库和模拟平台接口覆盖层级调用、配置、授权回调、凭据加密、迁移、映射、分页及超时/失败；验证入口不能绕过操作层。真实 Oura 登录和同步仅在具备授权的环境中进行，并明确记录实际验证范围。不要在没有明确实施需求时创建 Web 服务、Skill 或后台任务的空壳。
